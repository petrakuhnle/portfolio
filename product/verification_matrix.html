What was different here

Must-have requirements were agreed in writing with the client before build, and I gradually pushed for others to write them too, so alignment rested on requirements, not designs alone. That set a tight MVP boundary and prevented refactoring.

The hard part was getting everyone to agree on what was Must-have. Applying the lesson from Use Case 1, we decided, wrote and reviewed the Must-haves first, with design and requirements agreed with the client, from user journeys and wireframes to a hi-fi prototype that set the MVP and prevented development refactoring.

Key design decisions

The central question I kept asking: which job role needs which view and filter? An engineer working on one verification method filters per method; a decision maker reviewing a requirement set filters for its status. Same matrix, different scenarios. The role-and-view thread continues in Use Case 3, Review Center.

  • Views and filters per roleengineers vs decision makers
  • Linked to the requirementsbeats a separate Excel matrix
  • MVP boundarysmall and extendable

Lessons learned

The prototype drove the discovery.

  1. Prototype as discovery tool

    Its detail level surfaces the questions that define the MVP, what if one method isn't done yet, do you need to know who was assigned and reach them? A small system that ships is worth more than a complete one that never does.

  2. Non-expert as an advantage

    I used my non-expert status to ask instead of assume. An expert-as-designer risks leaving their own bias undetected, or hesitating to question a senior engineer or client.

  3. AI still needs real users

    AI knows job roles generally, not a company's specifics, so AI-generated prototypes still need testing with real users; unsupervised cycles grow scope creep and inconsistencies fastest.
