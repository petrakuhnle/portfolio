The hard part wasn't the matrix, it was getting everyone to agree on what was Must-have. Applying the lesson from Use Case 1, we decided, wrote and reviewed the Must-haves first, with design and requirements agreed with the client, from user journeys and wireframes to a hi-fi prototype that set the MVP and prevented development refactoring.

05Key design decisions

The central question I kept asking: which job role needs which view and filter? An engineer working on one verification method filters per method; a decision maker reviewing a requirement set filters for its status. Same matrix, different scenarios. The role-and-view thread continues in Use Case 3, Review Center.

06Lessons learned

The prototype did more than show the design. It drove the discovery.

01
Prototype as discovery toolIts detail level surfaces the questions that define the MVP, what if one method isn't done yet, do you need to know who was assigned and reach them? A small system that ships is worth more than a complete one that never does.
02
Non-expert as an advantageI used my non-expert status to ask instead of assume. An expert-as-designer risks leaving their own bias undetected, or hesitating to question a senior engineer or client.
03
AI still needs real usersAI knows job roles generally, not a company's specifics, so AI-generated prototypes still need testing with real users; unsupervised cycles grow scope creep and inconsistencies fastest.
